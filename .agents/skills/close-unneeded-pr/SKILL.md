# Close Unneeded PR

## 目的
GitHub PR が現行リポジトリ構成に不要かを調査し、根拠が十分な場合だけ理由付きで整理する。

このスキルは単なる `gh pr close` 手順ではない。必ず「なぜ不要なのか」をリポジトリの実態から確認してから進める。

## 使うべき場面
- 不要な PR を整理したいとき
- 自動生成された PR が現行構成に合っているか怪しいとき
- 古い前提技術に基づく PR を閉じたいとき
- コメント付きで PR をクローズしたいとき
- 複数 PR を同じ理由でまとめて整理したいとき

## 対象
- 現行構成に存在しない設定ファイルやサービスを前提にした PR
- すでに使っていない技術、ホスティング、ライブラリ前提の PR
- 実装や依存関係と噛み合わない自動生成 PR
- 誤検知や古い前提で作られた保守 PR

## 非対象
- 判断根拠がリポジトリから確認できない PR
- ユーザーの明示確認なしにクローズすべきでない PR
- レビューで解決できる変更提案や、単に優先度が低いだけの PR

根拠が弱い場合はクローズに進まず、追加確認事項を提示する。

## 必須ルール
1. 先に PR を読む。タイトル、本文、変更ファイル、状態、作成者を確認する。
2. 先にリポジトリを調べる。PR の前提技術や設定が現行構成に存在するか確認する。
3. 根拠が十分な場合だけ「不要」と判断する。
4. コメント案は理由、補足、クローズ意図を含める。
5. コメント投稿とクローズの前に、必ずユーザーへ確認を取る。
6. 実行後は PR 状態とコメント反映を確認する。
7. サンドボックスで `gh` が失敗したら、認証と権限の切り分けを行う。

## 実行フロー

### 1. 対象 PR を把握する
- PR 番号の一覧を受け取る。
- `gh pr view` で以下を確認する。
  - `number`
  - `title`
  - `body`
  - `state`
  - `author`
  - `files`
  - `url`

複数 PR がある場合は、共通理由で閉じられるかも見る。

### 2. PR の前提を抽出する
- PR 本文と変更ファイルから、修正が依存している前提を列挙する。
- 例:
  - `firebase.json` がある前提
  - Firebase Hosting を使っている前提
  - 特定のライブラリや SaaS を導入済みという前提

### 3. リポジトリ実態を確認する
- ファイル有無、設定、依存関係、ドキュメント、ビルド設定を読む。
- まずは次を優先して確認する。
  - 変更対象ファイルが実在するか
  - `package.json` などの依存関係
  - デプロイ設定やホスティング設定
  - README や docs に残る古い記述

注意:
- README に古い記述が残っていても、実運用の設定や依存が無ければ「過去の名残」として扱える。
- 技術名がスキル一覧や実績欄にあるだけでは、現行デプロイ基盤として使用中とは断定しない。

### 4. 判断する
次のすべてを満たす場合のみ「不要」と判断してよい。
- PR の前提が現行構成と矛盾している
- 根拠をリポジトリから具体的に示せる
- 代替説明がある程度排除できる

不要と判断しないケース:
- 設定ファイルは無いが、別の場所で同等設定をしている可能性が高い
- 外部サービス利用の有無がリポジトリだけでは分からない
- 単に自分がまだ見つけていないだけの可能性が高い

### 5. ユーザー確認前の出力を作る
クローズ前に、必ず次の形式でまとめる。

#### 調査結果
- 各 PR の要点
- 不要と考える根拠
- 残っている曖昧さ

#### クローズ方針
- `close` か `needs confirmation` か
- 複数 PR をまとめて同一文面で処理するか

#### コメント案
- 1 件ごとの文面、または共通文面

#### 実行予定コマンド
- `gh pr comment <number> --body '...'`
- `gh pr close <number>`

この段階でユーザー確認を取り、了承が出るまで実行しない。

### 6. 実行前チェック
- `gh auth status` を確認する。
- サンドボックス内で失敗し、認証情報がサンドボックス外では有効な可能性がある場合は、切り分けのためにサンドボックス外で再試行する。
- 書き込み系コマンドは必要なら権限承認を取って実行する。

### 7. 実行する
- 先にコメントを投稿する。
- 次に PR をクローズする。
- 複数件ある場合、まず全件コメント、その後全件クローズでもよい。

### 8. 実行後確認
- `gh pr view <number> --json state,comments,url` を確認する。
- `state` が `CLOSED` であることを確認する。
- 自分が投稿したコメントが反映されていることを確認する。

## コメント案の原則
- 1 文目で「なぜ今の構成に不要か」を明言する。
- 2 文目で古い記述や残存情報がある場合の補足を入れる。
- 最後に「そのためクローズする」と明言する。

例:

```text
現在このリポジトリでは Firebase をデプロイ基盤として使用していないため、`firebase.json` を前提にしたこの変更は現行構成には不要です。
リポジトリ内に残っている Firebase 関連の記述は過去の名残なので、必要なら別途整理します。
そのため、この PR はクローズします。
```

## 出力フォーマット
常に次の順序で出力する。

### 1) 調査結果
- PR ごとの概要と根拠

### 2) クローズ可否
- `close` または `needs confirmation`

### 3) コメント案
- 実際に投稿する文面

### 4) 実行予定コマンド
- 実行前のみ

### 5) 実行後確認結果
- 実行後のみ

## 返信時の姿勢
- 根拠が弱いのに断定しない。
- ユーザーの依頼が簡潔でも、調査を先に行う。
- コメントは簡潔に保ち、感情的な表現を避ける。
- 複数 PR は同じ理由で閉じられるならまとめて扱う。

## 最終チェックリスト
- PR の変更前提を明確にした
- リポジトリ実態で裏を取った
- 不要判断の根拠を短く説明できる
- コメント案を作った
- ユーザー確認を取った
- 実行後に `state` とコメントを確認した
