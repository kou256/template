# Commit Staged Changes

## 目的
ステージ済み（`git add` 済み）の差分だけを対象に、リポジトリ規約に沿ったコミットメッセージを生成し、ユーザーの承認を得てからコミットします。
差分が単一の論理的なまとまりに収まらず「一言で要約できない」場合は、無理に1つのメッセージへ押し込めず、分割コミットを提案します。
分割するかどうかはコミット履歴の読みやすさに直結するため、ここをスキルの中心的な判断として扱います。

## 対象とスコープ
- 対象は**ステージ済みの差分のみ**です。`git diff --staged` に現れる変更だけを見ます。
- 未ステージの変更やワークツリーの状態は、ユーザーに知らせる以外には変更しません（勝手に `git add .` しません）。
- コミットの実行・分割の実行は、必ずユーザーの承認後に行います。

## 最初に確認すること
1. `git diff --staged --stat` と `git diff --staged` でステージ済み差分を取得します。
2. ステージ済み差分が空であれば、その旨を伝え、未ステージの変更があれば「`git add` が必要かもしれません」と知らせて止まります。勝手にステージしません。
3. このリポジトリのコミット規約を `references/commit-convention.md` で確認します。

## 必須ルール
1. コミットメッセージは `references/commit-convention.md` の規約（`<種類>: <絵文字> 説明`）に従います。種類プレフィックスと絵文字を**必ず**組み合わせます。
2. メッセージは推測で断定せず、**差分から読み取れる事実**に基づいて書きます。差分から目的が読み取れない場合は、コミットせずユーザーに意図を確認します。
3. コミット実行前に必ずメッセージ案を提示し、ユーザーの承認を得ます。承認なしにコミットしません。
4. 分割が妥当と判断したら、単一メッセージへ無理にまとめず分割を提案します。判定基準は `references/split-guide.md` に従います。
5. 分割・コミットの実行は承認後に限ります。提案段階ではワークツリーやインデックスを変更しません。

## 標準フロー

### 1. 差分を読み、まとまりを判定する
ステージ済み差分を読み、変更が**1つの論理的なまとまり（1つの目的）**で説明できるかを判断します。
判定の詳細な基準とサインは `references/split-guide.md` を参照します。要点は次のとおりです。

- 種類（feat / fix / docs など）が混在している
- 互いに無関係な複数の責務・ディレクトリにまたがる
- subject を書こうとすると「〜と〜」「かつ」で複数の事柄をつながないと説明できない
- 機能追加・リファクタ・整形が同居している

これらに当てはまるほど、分割の価値が高くなります。

### 2A. 単一コミットの場合
1. `references/commit-convention.md` に沿ってメッセージ案を1つ作ります。
2. `references/output-template.md` の「単一コミット」形式で、差分サマリとメッセージ案を提示します。
3. ユーザーが承認したら `git commit` を実行します。修正指示があれば反映して再提示します。

### 2B. 分割を提案する場合
1. ステージ済み差分を、まとまりごとに2〜4個程度のグループへ分けます。各グループに対象ファイル（必要ならハンク）とメッセージ案を割り当てます。
2. `references/output-template.md` の「分割コミット」形式で、グループ一覧・対象ファイル・各メッセージ案を提示し、承認を求めます。
3. 承認後、グループごとに次のようにコミットします。インデックスを全リセットすると、もともと未ステージだった変更と区別がつかなくなり巻き込む危険があるため、全リセットはしません。
   - 最初のグループに含めない対象だけを `git reset HEAD <対象外のパス>` でアンステージします（もともと未ステージだった変更には触れません）。
   - ステージに残った最初のグループの対象を、そのグループのメッセージで `git commit` します。
   - 以降のグループは、対象を `git add <paths>` でステージしてから順次 `git commit` します。
   - 1ファイルにステージ済みと未ステージのハンクが混在する場合は、未ステージ分を巻き込まないよう `git add -p` でハンク単位に選択します。
4. ユーザーが分割を望まない場合は、単一コミット（2A）に切り替えます。

ステージ済み差分のみを対象とするため、もともと未ステージだった変更を巻き込まないことを最優先にします（インデックスの全リセットは行いません）。

## チェックリスト
- [ ] 対象はステージ済み差分のみで、未ステージ分を勝手に含めていないか
- [ ] メッセージが `<種類>: <絵文字> 説明` の規約に合っているか
- [ ] メッセージが差分から読み取れる事実に基づいているか
- [ ] 単一で説明できない差分を無理に1コミットへ押し込めていないか
- [ ] コミット／分割の実行前にユーザーの承認を得たか
- [ ] 分割時、各グループのステージ操作で差分を失わず、かつ未ステージの変更を巻き込んでいないか

## ブランチ名規約

このスキルはコミットメッセージ規約に加えて、**ブランチ名規約の正**も持ちます。
ブランチを切るとき、およびブランチ名を尋ねられたときは `references/branch-convention.md` を参照します。

形式は `<種類>/<kebab-case-説明>` で、プレフィックスは feat / fix / docs / refactor / chore / test / ci の7種に限定します（`feature/` は使いません）。
コミットメッセージの種類のほうが細かいため、`style`・`perf`・`deps` などは対応表に従って寄せます。

## 参照ファイル

- `references/output-template.md` — 提案の出力フォーマット（単一／分割）
