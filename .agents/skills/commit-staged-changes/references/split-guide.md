# 分割コミットの判定と分け方

コミット履歴は後から差分を読み解くための記録です。1つのコミットが1つの意図に対応していると、レビューも巻き戻しも容易になります。
「一言で要約できないほど多い」差分を1コミットに押し込めると、この読みやすさが失われます。そこで、まとまりごとの分割を提案します。

## 分割を提案するサイン
次のいずれかに当てはまるほど、分割の価値が高くなります。

1. **種類が混在している** — feat と fix、fix と refactor、機能変更と docs などが同じ差分に同居している。
2. **無関係な責務にまたがる** — 例えば認証の修正と請求ロジックの変更など、互いに依存しない関心事が混ざっている。
3. **subject が1つにまとまらない** — メッセージを書こうとすると「〜と〜」「かつ」「ついでに」で複数の事柄をつながないと説明できない。
4. **ディレクトリ／レイヤーが大きく分かれる** — 例えば UI 層とインフラ層、無関係な複数パッケージにまたがる。
5. **付随変更が独立している** — 本筋と切り離せる整形・リネーム・依存更新が混ざっている。

逆に、変更が多くても**1つの目的に向かって一貫している**なら、無理に分割しません。行数の多さだけで分割を判断しないでください。判断軸は「1つの意図で説明できるか」です。

## 分け方の指針
- グループ数は2〜4個程度を目安にします。細かく割りすぎると履歴がかえって追いにくくなります。
- ファイル単位で分けられるのが理想です。1ファイル内に複数の関心事が混在する場合のみ、`git add -p` によるハンク単位の分割を検討します。
- 依存関係のある変更は、ビルドやテストが通る順序を意識して並べます（例: 先に基盤、後に利用側）。
- 各グループに、`commit-convention.md` に沿ったメッセージ案を1つずつ割り当てます。

## 提案時の注意
- 提案段階ではインデックスもワークツリーも変更しません。あくまで案として提示します。
- どのファイルがどのグループに入るかを明示し、ユーザーが過不足を確認できるようにします。
- ユーザーが「分割不要」と判断した場合は、主目的の種類でまとめた単一コミット案に切り替えます。
