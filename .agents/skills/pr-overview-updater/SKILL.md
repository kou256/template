# PR Overview Updater

## 目的
GitHub PR の差分を読み取り、変更内容が伝わる本文へ再構成する。

このスキルは単に要約文を出すだけではない。既存本文から残すべき情報を拾い、更新前に本文案を見せ、承認後にだけ PR 本文を更新する。

## 使うべき場面
- PR の概要が古い、薄い、または空欄のとき
- 差分から PR 本文を作り直したいとき
- PR summary を日本語で整理したいとき
- レビュー前に PR 本文を読みやすく整えたいとき
- 既存本文の Issue 参照や補足を残しつつ再生成したいとき

## 入力
- PR 番号
  - 例: `123`
- PR URL
  - 例: `https://github.com/owner/repo/pull/123`

URL を受け取った場合は PR 番号を抽出して扱う。

## 前提
- `gh` CLI がインストールされていること
- `gh auth status` が成功すること
- 対象 PR にアクセスできること

## 必須ルール
1. 先に `gh auth status` で認証を確認する。
2. 先に `gh pr view` で PR のタイトル、本文、変更ファイル、URL、状態を確認する。
3. 先に `gh pr diff` で差分を読む。
4. 新しい本文は必ずプレビューを提示してから扱う。
5. `gh pr edit` を実行するのは、ユーザー承認後だけにする。
6. 更新後は `gh pr view` で本文反映を確認する。
7. テスト内容が差分や本文から判断できない場合、`# テスト` セクションは書かない。
8. 既存本文は丸ごと引き継がない。残すのは `Issue参照` と短い `補足メモ` に限定する。

## 同期モード（push 後の自動起動）

`pr-summary-sync` プラグインの hook から起動された場合だけ、通常フローの前に
「そもそも更新が必要か」を判定する段を挟みます。**ユーザーが手動でこのスキルを
呼んだ場合は、この節を適用しません**（手動起動は常に本文を作り直す依頼です）。

判定の手順:

1. hook が渡した PR 番号、push されたコミット一覧、現在の本文を読む。
2. 現在の本文が、push された変更を過不足なく説明できているかを判定する。
   判断がつかない場合だけ `gh pr diff <number>` を読む。
3. 説明できていれば、`# 概要` の作成に進まず「PR #<number> の本文は現在の差分と
   整合しています」と1行だけ返して終了する。GitHub には一切書き込まない。
4. 説明できていなければ、通常フローの `### 3. 差分を取得する` 以降に合流する。
   hook から渡されるのはコミット一覧とファイル一覧だけで差分本文は含まれないため、
   `### 4.` に直接合流すると差分を読まないまま要約を書くことになる。

ズレていると判断する例:

- push したコミットが入れた変更が、本文のどこにも書かれていない
- 本文が説明している内容が、現在の差分から消えている
- 本文が空、またはテンプレートの未記入状態のまま

必須ルール5（`gh pr edit` はユーザー承認後だけ）は、同期モードでも変わりません。

## 実行フロー

### 1. 入力を解釈する
- PR 番号または URL を受け取る。
- URL の場合は PR 番号を抽出する。
- 入力が欠けている場合は、PR 番号または URL を求める。

### 2. 認証と PR 状態を確認する
- `gh auth status` を実行する。
- `gh pr view <number> --json number,title,body,files,url,state` を実行する。
- PR が存在しない場合は終了する。
- PR が `CLOSED` または `MERGED` の場合は、その状態を示して続行可否を確認する。

### 3. 差分を取得する
- `gh pr diff <number>` を実行する。
- 変更ファイル一覧と差分から、何を変えた PR なのかを把握する。
- 差分が空、または取得に失敗した場合は、本文更新に進まず原因を伝える。

### 4. 概要を要約する
- 差分全体から主な変更点を 1-3 個の箇条書きにまとめる。
- 変更理由の断定は避け、差分から確認できる事実を優先する。
- 実装詳細を列挙しすぎず、レビュー時に把握したい変更単位でまとめる。

要約の観点:
- 何を追加したか
- 何を修正したか
- 何を削除・整理したか
- どの領域に影響するか

### 5. テスト情報を抽出する
- 既存本文や差分にテスト、確認手順、実行コマンド、スクリーンショット説明があれば `# テスト` にまとめる。
- 推測だけでテスト内容を捏造しない。
- 判断できない場合は `# テスト` セクション自体を省略する。

### 6. 既存本文から引き継ぐ情報を抽出する
引き継ぎ対象は2種類あり、**行き先のセクションが違う**。

`# 関連 issue` に引き継ぐもの:
- Issue / PR 参照
  - `#123`
  - `owner/repo#123`
  - GitHub Issue / PR URL
  - `Closes`, `Refs`, `Related` などの参照行

`# 補足` に引き継ぐもの:
- 短い補足メモ
  - 1-3 行程度の自由記述
  - レビュー時に残す価値がある前提や注意書き

引き継がないもの:
- 長い説明文
- チェックリスト全体
- テンプレートの未記入項目
- コードブロック
- 自動生成ログ

Issue 参照がなければ `# 関連 issue` は書かない。補足メモがなければ `# 補足` は書かない。
**Issue 参照を `# 補足` に混ぜない。** リポジトリの PR テンプレートが4節構成なので、参照の置き場所がずれると、人が書いた PR とこのスキルが書いた PR で形が変わる。

### 7. 新しい本文案を作る
本文は次のテンプレートで組み立てる。空のセクションは出さない。

```md
# 概要
- {PR内の主な変更}
- {必要なら2点目以降}

# テスト
- {差分や本文から確認できるテスト内容}

# 補足
- {引き継いだ補足メモ}

# 関連 issue
{Closes #123 / Refs #123 などの参照行}
```

ルール:
- `# 概要` は必須
- `# テスト` は情報がある場合のみ
- `# 補足` は引き継ぐ補足メモがある場合のみ
- `# 関連 issue` は Issue 参照がある場合のみ
- セクションの順序はこのとおりに固定する（リポジトリの PR テンプレートと同じ並び）
- 日本語で簡潔に書く

### 8. 更新前プレビューを提示する
更新前は必ず次の順序で提示する。

#### PR情報
- PR 番号
- タイトル
- URL

#### 新しい本文案
```md
{生成した本文}
```

#### 実行予定コマンド
- `gh pr edit <number> --body-file <temp-file>`

この段階ではまだ更新しない。ユーザー承認を待つ。

### 9. 承認後に更新する
- ユーザーが承認したら `gh pr edit` で本文を更新する。
- 反映後、`gh pr view <number> --json body,url` を再取得する。
- 本文が期待どおり更新されたことを確認する。

### 10. 結果を報告する
- 更新した PR 番号と URL
- 反映確認の結果
- 必要なら、残った懸念や未反映事項

## エラー時の扱い
- `gh` 未認証:
  - `gh auth status` の失敗を伝え、認証が必要だと示して終了する。
- PR が存在しない:
  - 番号や URL の確認を促して終了する。
- PR が `CLOSED` / `MERGED`:
  - 状態を明示し、更新を続けるか確認する。
- 差分が空または取得不能:
  - 本文更新を止め、差分取得失敗として扱う。
- 更新承認が得られない:
  - 本文案だけ提示し、GitHub 更新は行わない。

## 出力フォーマット
常に次の順序で出力する。

### 1) PR情報
- PR 番号
- タイトル
- URL
- 状態

### 2) 差分要約
- `# 概要` に入れる予定の要点

### 3) 新しい本文案
- 実際に更新する Markdown 本文

### 4) 実行予定
- 承認待ちか、更新済みかを明示する

### 5) 更新後確認結果
- 更新実施後のみ

## 返信時の姿勢
- 差分に基づかない断定をしない。
- 情報が足りない場合も、まず取得できる情報を集めてから判断する。
- 本文は簡潔に保ち、箇条書き中心で読みやすくする。
- 既存本文の情報は無制限に残さず、重要なものだけ選ぶ。
- ユーザー承認前に GitHub へ書き込まない。

## 例

**入力例 1**
`PR #123 の概要を差分から作り直して`

**入力例 2**
`https://github.com/example/repo/pull/456 の PR 本文を更新したい`

## 最終チェックリスト
- PR 番号または URL を解釈した
- `gh auth status` を確認した
- `gh pr view` と `gh pr diff` の両方を読んだ
- `# 概要` を差分ベースで作成した
- `# テスト` を必要時だけ含めた
- `# 補足` に短いメモだけを引き継いだ
- `# 関連 issue` に Issue 参照を引き継いだ
- 更新前にプレビューを出した
- ユーザー承認後だけ更新した
- 更新後に反映確認をした
